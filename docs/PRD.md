## 1. 문제와 제품 목표

시니어와 가족은 건강정보 채널이 실제 치료·복약 행동을 위험하게 바꾸도록 유도하는지, 건강
불안을 구매로 연결하는지, 주장과 발화자의 출처를 확인할 수 있는지 구독 목록에서 한 번에
살펴보기 어렵다. 반복·대량 생산되는 채널도 사람이 직접 여러 영상을 비교해야 알아차릴 수 있다.

이 제품은 인증한 사용자의 YouTube 구독 채널을 분석해 다음 두 정보를 분리해서 제공한다.

- `콘텐츠 리스크`: 영상 내용이 건강 행동에 끼칠 수 있는 위험을 LLM이 루브릭으로 평가한 값
- `공장형 가능성`: 채널의 공개 메타데이터에서 반복·대량 생산 신호를 규칙으로 계산한 값

사용자는 근거와 한계를 검토하고 직접 채널을 선택한다. 시스템은 최종 확인을 받은
`subscriptionId`만 구독 해제한다.

## 2. 목표와 비목표

### 2.1 목표

- 구독 목록 전체를 누락 없이 가져오고 건강 관련 후보를 선별한다.
- 최신성과 채널 대표성을 함께 보기 위해 최신 2개와 인기 3개 영상을 평가한다.
- 두 점수와 계산 이유, 평가 표본, 실패와 한계를 같은 결과에서 확인하게 한다.
- 선택, 확인, 실행을 분리해 사용자가 비가역 액션을 통제하게 한다.
- 점수·프롬프트·스키마 버전을 남겨 결과의 출처를 추적하게 한다.

### 2.2 비목표

- 건강정보의 사실 여부, 법 위반, 사기, 의료인 자격을 확정하지 않는다.
- Google Data Portability, Takeout, 시청 기록, 좋아요·싫어요와 추천 피드 제어를 다루지 않는다.
- 조회 수나 구독자 수로 신뢰도를 판단하지 않는다.
- 합성 콘텐츠 공개 표시를 허위정보 또는 기만으로 해석하지 않는다.
- 채널을 자동 선택하거나 자동 구독 해제하지 않는다.
- 기존 `openai-workshop` 데모 코드·가정·점수식을 재사용하지 않는다.

## 3. 사용자와 핵심 시나리오

주 사용자는 자신의 계정을 정리하려는 시니어 또는 본인의 계정을 함께 검토하는 가족이다.
타인의 계정을 대리 관리하는 기능은 없다.

### 시나리오 A — 분석

1. 사용자가 제품의 데이터 사용 목적과 쓰기 권한을 확인하고 Google 계정을 연결한다.
2. 시스템이 전체 구독 목록을 수집하고 진행 상태를 표시한다.
3. 건강 관련 후보 채널만 영상 표본과 점수를 계산한다.
4. 사용자가 채널별 두 점수, 이유, 영상 근거, 표본과 한계를 검토한다.

### 시나리오 B — 구독 해제

1. 사용자가 기본 미선택인 체크박스에서 채널을 직접 고른다.
2. 확인 모달에서 채널명과 총개수를 확인한다.
3. 사용자가 최종 승인하면 시스템이 선택된 구독만 해제한다.
4. 성공과 실패를 채널별로 확인하고 실패 항목만 다시 선택해 재시도한다.

## 4. 기능 요구사항

### 4.1 인증과 세션

- `FR-AUTH-001`: 시스템은 Google OAuth 웹 서버 흐름으로 현재 사용자를 인증해야 한다.
- `FR-AUTH-002`: 시스템은 구독 조회와 삭제에 필요한 승인 범위, 사용 목적과 삭제 효과를
  동의 화면 직전에 설명해야 한다.
- `FR-AUTH-003`: OAuth `state`를 일회성 세션 값과 대조하고 불일치·재사용 콜백을 거부해야 한다.
- `FR-AUTH-004`: OAuth 토큰은 서버에서만 취급하고 브라우저 JavaScript, URL, 로그와 LLM 입력에
  노출하지 않아야 한다.
- `FR-AUTH-005`: 사용자는 연결 해제와 저장 데이터 즉시 삭제를 실행할 수 있어야 한다.
- `FR-AUTH-006`: 토큰 만료·철회 시 분석이나 삭제를 실행하지 않고 재연결 상태를 표시해야 한다.

### 4.2 구독과 채널 수집

- `FR-COLLECT-001`: `subscriptions.list`의 모든 페이지를 순회해 전체 구독을 수집해야 한다.
- `FR-COLLECT-002`: 각 구독에 `subscriptionId`, `subscribedAt`, `channelId`, 이름, 설명과
  썸네일을 보존해야 한다.
- `FR-COLLECT-003`: 채널 ID를 최대 50개씩 묶어 상세정보와 uploads 재생목록 ID를 보강해야 한다.
- `FR-COLLECT-004`: 없거나 삭제된 채널은 전체 작업을 중단하지 않고 채널별 실패로 기록해야 한다.
- `FR-COLLECT-005`: 업로드 재생목록을 순회해 최근 90일 패턴 지표와 최신 20개 메타데이터를
  확보해야 한다.
- `FR-COLLECT-006`: 비공개·삭제 placeholder는 평가 표본에서 제외하고 제외 이유를 집계해야 한다.
- `FR-COLLECT-007`: 채널명·설명과 최신 영상 제목·설명에 고감도 건강 분류 정책을 적용해 후보를
  선별하고 정책 버전을 기록해야 한다.

### 4.3 영상 표본과 보강

- `FR-SAMPLE-001`: 건강 후보마다 uploads 재생목록에서 최신 공개 영상 2개를 선택해야 한다.
- `FR-SAMPLE-002`: 건강 후보마다 `search.list` 조회 수 내림차순 결과에서 인기 영상 3개를
  선택해야 한다.
- `FR-SAMPLE-003`: 최신·인기 표본을 `videoId`로 중복 제거하고 각 선택 출처를 보존해야 한다.
- `FR-SAMPLE-004`: `videos.list`로 제목, 설명, 태그, 게시 시각, 길이, 조회 수, 공개 상태와
  `containsSyntheticMedia`를 보강해야 한다.
- `FR-SAMPLE-005`: `containsSyntheticMedia` 필드 부재를 `unknown`으로 저장해야 한다.
- `FR-SAMPLE-006`: API 검색 제한이나 쿼터로 일부 채널을 평가하지 못하면 성공한 채널과 섞어
  완료로 표시하지 않고 부분 완료와 누락 수를 보여줘야 한다.

### 4.4 공장형 가능성

- `FR-FACTORY-001`: 순수 규칙 엔진은 업로드 패턴 40점, 제목·설명 반복도 40점,
  합성 콘텐츠 표시 비율 20점의 감점을 계산해야 한다.
- `FR-FACTORY-002`: 같은 정규화 입력과 `factory-policy-v1`에는 같은 결과가 나와야 한다.
- `FR-FACTORY-003`: 항목별 점수, 원시 지표, 대표 반복 사례와 측정 상태를 저장해야 한다.
- `FR-FACTORY-004`: 측정 최소 표본을 충족하지 못한 항목은 0점이 아니라 `unmeasured`로
  구분해야 하며 총점에 임의 감점을 추가하지 않아야 한다.
- `FR-FACTORY-005`: 구독자 수, 조회 수와 채널 개설 연도 자체를 점수에 사용하지 않아야 한다.
- `FR-FACTORY-006`: `containsSyntheticMedia=true`는 합성 공개 비율에만 사용하고 콘텐츠 리스크에
  전달하지 않아야 한다.

### 4.5 영상 콘텐츠 리스크

- `FR-RISK-001`: LLM judge는 영상 콘텐츠, 영상 제목·설명과 채널 정보를 한 번의 루브릭 평가에
  입력받아야 한다.
- `FR-RISK-002`: judge는 행동 유도 0~40, 구매 유도 0~30, 출처 명확성 0~30 감점을 직접
  반환해야 한다.
- `FR-RISK-003`: judge는 감점마다 이유를, 가능한 경우 근거 문구와 시작 시각을 반환해야 한다.
- `FR-RISK-004`: judge는 확인하지 못한 정보를 추측하거나 외부 검색으로 보강하지 않아야 한다.
- `FR-RISK-005`: 합성 공개, 조회 수, 구독자 수와 업로드 빈도를 콘텐츠 감점 근거로 사용하지
  않아야 한다.
- `FR-RISK-006`: 코드는 JSON schema, 점수 범위, 합계, 안전 점수와 이유 존재만 검증하고
  LLM 판단의 의미를 별도 규칙이나 LLM으로 재채점하지 않아야 한다.
- `FR-RISK-007`: 영상 처리 실패 시 제목·설명만으로 점수를 대신 만들지 않아야 한다.
- `FR-RISK-008`: 모델, 프롬프트, 출력 스키마와 평가 시각을 결과에 기록해야 한다.

### 4.6 채널 집계와 결과

- `FR-RESULT-001`: 성공한 고유 건강 영상이 3개 이상일 때만 채널 리스크를 계산해야 한다.
- `FR-RESULT-002`: 채널 리스크는 `max(videoRisk) × 0.6 + avg(videoRisk) × 0.4`로 계산하고
  소수점 첫째 자리에서 반올림해야 한다.
- `FR-RESULT-003`: 콘텐츠 리스크는 70~100 `위험도 높음`, 40~69 `확인 필요`, 0~39
  `뚜렷한 위험 신호 없음`, 계산 불가 `표본 부족`으로 표시해야 한다.
- `FR-RESULT-004`: 채널별 판단 이유는 감점이 큰 영상부터 중복 의미를 제거해 최대 3개를
  표시해야 한다.
- `FR-RESULT-005`: 각 행은 채널명, 썸네일, 구독 시각, 두 점수·등급, 이유와 영상 제목,
  가능한 근거·타임스탬프, 평가 수와 한계를 표시해야 한다.
- `FR-RESULT-006`: 공장형 가능성과 콘텐츠 리스크를 하나의 종합점수·통합 등급으로 합치지
  않아야 한다.
- `FR-RESULT-007`: 분석 진행률은 수집, 후보 선별, 영상 평가, 집계 단계와 성공·실패 개수로
  표시해야 한다.

### 4.7 선택, 확인과 구독 해제

- `FR-ACTION-001`: 모든 채널 체크박스는 점수와 무관하게 기본 미선택이어야 한다.
- `FR-ACTION-002`: 확인 모달은 현재 선택된 채널명과 개수를 표시해야 한다.
- `FR-ACTION-003`: 서버는 현재 세션의 분석 결과에서 선택 가능한 `subscriptionId`인지 다시
  검증하고 클라이언트가 보낸 채널명이나 점수를 신뢰하지 않아야 한다.
- `FR-ACTION-004`: 최종 승인 전에는 `subscriptions.delete`를 호출하지 않아야 한다.
- `FR-ACTION-005`: 일회성 confirmation ID는 사용자, 분석 작업, 정렬된 subscription ID 목록의
  해시와 만료 시각에 결합되어야 한다.
- `FR-ACTION-006`: 삭제 요청은 채널별로 독립 실행하고 성공, 이미 없음, 인증 실패, 쿼터·일시
  실패와 영구 실패를 구분해야 한다.
- `FR-ACTION-007`: 재시도 UI는 실패 항목만 다시 선택하고 새 confirmation ID를 발급해야 한다.
- `FR-ACTION-008`: 성공한 행은 즉시 `구독 해제됨`으로 바꾸고 같은 구독의 중복 삭제를 막아야 한다.

## 5. 점수 정책

### 5.1 방향과 분리

```text
생산 건전성 점수 = 100 - 공장형 가능성
영상 안전 점수 = 100 - 영상 콘텐츠 리스크
```

화면에는 위험성이 클수록 값이 커지는 `공장형 가능성`과 `콘텐츠 리스크`를 우선 표시한다.
건전성·안전 점수는 내부 파생값으로 저장할 수 있으나 화면에서 혼동되는 제3의 점수로 강조하지
않는다.

### 5.2 LLM 채점 앵커

채점은 연속 정수 범위를 허용하되 다음 앵커를 프롬프트와 eval 기준으로 사용한다.

| 항목 | 0점 앵커 | 중간 앵커 | 최대점 앵커 |
|---|---|---|---|
| 행동 유도 | 설명 또는 보조 제안이며 치료 대체 없음 | 위해 가능 행동을 직접 권하나 제한·상담 맥락 존재 | 약·치료 중단·변경, 진료 회피 또는 대체요법 전환을 직접 지시 |
| 구매 유도 | 거래 연결 없음 | 건강 주장과 상품·구매 경로가 연결됨 | 치료·예방 주장과 직접 구매 경로에 공포·긴급성·희소성까지 결합 |
| 출처 명확성 | 핵심 주장과 발화자·근거가 구체적으로 추적 가능 | 일부 이름·자격·자료는 있으나 핵심 주장과 연결이 약함 | 익명 권위에 의존하고 발화자·기관·연구를 확인할 단서가 없음 |

단순 제품명, URL, 가격, 협찬 공개만으로 구매 유도 최대 감점을 주지 않는다. 단순 식습관·운동
제안은 위해 가능성, 기존 치료 대체 여부와 개인차·전문가 상담 안내를 함께 본다.

## 6. 상태 모델

```ts
type AnalysisJobStatus =
  | "queued"
  | "collecting_subscriptions"
  | "collecting_channels"
  | "classifying_candidates"
  | "sampling_videos"
  | "scoring_factory"
  | "judging_videos"
  | "aggregating"
  | "completed"
  | "partial"
  | "failed";

type MeasurementStatus = "measured" | "unmeasured" | "partial";
type EvidenceStatus =
  | "completed"
  | "not_health_related"
  | "unavailable"
  | "blocked"
  | "timeout"
  | "provider_error"
  | "schema_invalid";
```

0점은 평가 결과 위험 신호가 없다는 뜻이다. `unmeasured`, `unavailable`과 실패 상태를 0점으로
직렬화하거나 UI에서 같은 모양으로 표시하지 않는다.

## 7. 비기능 요구사항

- `NR-SEC-001`: 비밀정보는 환경변수 또는 서버 비밀 저장소에서만 읽는다.
- `NR-SEC-002`: 모든 상태 변경 요청은 CSRF 방어, 세션 소유권과 입력 스키마 검증을 거친다.
- `NR-PRIV-001`: 분석·API 데이터는 기본 24시간 TTL 후 삭제하며 사용자는 즉시 삭제할 수 있다.
- `NR-PRIV-002`: LLM에는 공개 영상 URL과 공개 메타데이터만 보내며 사용자 ID, 이메일,
  `subscriptionId`, OAuth 토큰은 보내지 않는다.
- `NR-OBS-001`: 로그는 `jobId`, 단계, 공급자 상태 코드, 시도 횟수와 지연 시간만 기록하고
  토큰·원문 설명·LLM 근거·subscription ID는 기록하지 않는다.
- `NR-REL-001`: 외부 API의 재시도 가능 오류는 제한된 지수 백오프로 처리하고 전체 재시작 없이
  채널·영상 단위로 실패를 격리한다.
- `NR-UX-001`: 점수는 색상만으로 구분하지 않고 텍스트 등급과 설명을 함께 제공한다.
- `NR-UX-002`: 키보드만으로 선택·모달 확인·취소·재시도를 수행할 수 있어야 한다.
- `NR-PERF-001`: 수집은 API가 허용하는 최대 배치를 사용하고 LLM 동시 실행 수는 구성값으로
  제한한다.
- `NR-COMP-001`: 공개 배포 전에 YouTube API 파생 지표 사용에 대한 컴플라이언스 검토와 필요한
  승인을 완료해야 한다.

## 8. 완료 조건

1. 테스트 계정의 모든 구독 페이지를 수집하고 채널별 수집 실패를 분리한다.
2. 최신 2개·인기 3개 선택과 `videoId` 중복 제거를 fixture로 재현한다.
3. 공장형 세 항목이 `factory-policy-v1` fixture에서 결정적으로 계산된다.
4. LLM judge의 경계·중복 감점·불충분 근거 사례가 eval 기대 범위를 만족한다.
5. 3개 미만 성공 표본에서 채널 리스크를 계산하지 않는다.
6. 결과 화면이 두 점수, 이유, 영상, 표본과 한계를 모두 표시한다.
7. 어떤 점수에서도 체크박스가 자동 선택되지 않는다.
8. 확인 전 삭제 호출이 없고 부분 실패 후 실패 항목만 재시도된다.
9. lint, typecheck, unit, integration, judge eval과 핵심 E2E가 통과한다.
10. 저장소와 클라이언트 번들에 API 키·OAuth 토큰·사용자 데이터가 없다.
